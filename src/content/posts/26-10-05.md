最近折腾 Dream Skin 给 Codex 换肤，过程中攒了一堆疑问，也顺手做了一次问答整理。这篇文章把三个核心问题讲清楚：**Dream Skin 到底是什么、DOM / CDP / Safe CSS 各自干嘛的、安装源和运行副本的区别。**

## 一、Dream Skin 是什么：给 Codex 做"换肤外挂"

**Dream Skin 不是简单给 Codex 换张壁纸，而是给 Codex 桌面端做"换肤外挂"；Miku 只是其中一套皮肤内容包。**

### 三层关系：Codex、Dream Skin、Miku

把 Codex 想成一个用网页技术搭起来的桌面软件。

- **Codex 桌面端**：真正干活的宿主应用，有对话、输入框、项目、设置等原生界面。
- **Dream Skin**：外观引擎，负责连进 Codex 页面，找到各种组件，铺背景、改样式、加载主题。
- **ChatGPT Miku 主题包**：具体皮肤内容，提供图片、颜色、局部样式。

这三层版本互相独立。Codex 更新、Dream Skin 更新、Miku 更新，不是一回事。所以验收时要同时记录：**宿主版本、引擎版本、主题版本**。

### Dream Skin 为什么能改桌面应用界面

因为 Codex 桌面端底层用的是 **Chromium** 网页渲染技术。界面里的按钮、侧栏、消息、输入框，本质上还是 HTML 元素和 CSS 样式。

Dream Skin 通过本机回环地址 `127.0.0.1` 上的 **CDP** 连接 Codex 页面，然后：

1. 找到真正的 Codex 界面页面；
2. 读取引擎样式和主题内容；
3. 注入脚本和 CSS；
4. 给组件打标记；
5. 主题根据标记改外观。

"注入"不是改 Codex 的 exe 或 `app.asar`，而是在运行时往页面里加代码和样式。文档里特别说：**这次修复没有修改 Codex 安装文件**，只是排查时读过 `app.asar` 确认结构。

### 启动脚本和动态页面

Dream Skin 有一堆脚本，负责安装、启动、应用社区主题、托盘控制、验证、恢复等。它还管理独立的 `cdp-profile` 目录，因为新版 Chromium 对默认用户数据目录的远程调试有限制。

但注意：**独立用户数据目录不等于一定有一个完全独立的备用应用实例。** 不能只看窗口数量判断进程影响。

Codex 页面是动态的：切对话、开设置、弹菜单、重建输入框，DOM 都会变。Dream Skin 用 `MutationObserver` 盯着页面变化，然后重新检查、重新绑定组件。所以"刚才找到过输入框"不代表现在还在。

### Miku 主题包里有什么

原版 Miku 包核心是四个文件：

- `background.png`：背景图，决定人物、色彩、构图、留白。
- `theme.json`：主题配置，比如图片焦点 `focusX/focusY`、明暗外观、任务页背景模式。
- `theme.css`：组件外观，比如侧栏、顶栏、消息、输入框、弹窗的背景、边框、圆角、阴影。
- `manifest.json`：包说明和校验，记录版本、平台、能力、文件大小、SHA-256 等。

`focusX=0.65`、`focusY=0.3` 不是把人物直接移动到窗口某个坐标，而是**图片显示位置偏好**。实际裁切还取决于图片比例、容器比例和缩放方式。

### Safe CSS 的能力边界

Dream Skin 有一份 `safe-css-policy.json`，规定主题 CSS 只能改哪些东西。允许的组件有 root、sidebar、main、header、home、thread、message、composer、dialog 等；允许状态有 hover、focus-visible；允许属性主要是背景、文字、边框、圆角、阴影、字体、间距、透明度、背景滤镜等。

但 **`display`、`position`、`z-index` 不在主题白名单里**。意思是：主题作者主要管视觉表达，引擎维护者管原生页面适配和底层布局。

Safe CSS 只是限制能力范围，不保证效果好看。比如文字颜色合规，仍可能看不清；透明度合规，仍可能被背景干扰阅读。

### 高透明度为什么要检查多层背景

屏幕上输入区域可能有很多层：

```text
背景图片 → 主区表面 → 任务滚动区域 → 底部装饰背景和渐变 → 输入框外壳 → 实际输入内容
```

把输入框外壳变透明，不代表外围装饰层也透明。Miku 的 `rgba(253, 252, 249, 0.05)` 只有 5% 不透明度，但如果后面有一层完全不透明白底，视觉上还是一大块白色。

还要区分：

- **`background-color: rgba(...)`**：只淡化背景颜色；
- **`opacity: 0.05`**：整个元素连同文字、图标、子元素一起变淡。

想"背景淡、文字清晰"，通常应调背景颜色的 **alpha**，而不是整个组件的 **opacity**。

### 之前对话为什么消失

引擎原本有一条规则，用来隐藏顶部装饰渐变：

```css
:is(
  .app-shell-main-content-top-fade,
  [data-app-shell-main-content-top-fade],
  [class*="_MainContentTopFade_"]
) {
  display: none !important;
}
```

但在当时的 Codex 里，带有 `data-app-shell-main-content-top-fade` 属性的容器，实际承载了主内容，包括正文和输入框。

于是引擎以为它只是渐变，把它 `display:none` 隐藏了，结果**整个主内容和输入框一起消失**。父容器被隐藏后，子节点自己的主题样式救不回来。

最终修复只移除了 `[data-app-shell-main-content-top-fade]` 这个选择器分支，保留另外两个装饰类名分支。这是引擎兼容修复，不是原版 Miku ZIP 的一部分。

### Codex 更新为什么容易出问题

Codex 更新可能改类名、属性、父子层级、输入框外壳、路由、渲染时机、装饰层位置，甚至改旧属性的职责。

最危险的情况是：**选择器仍然命中，但命中的元素职责已经变了。** `top-fade` 问题就是这种。

所以适配检查不能只问"命中几个"，还要问"命中的元素现在到底在干什么"。

### 日志成功不等于实际可用

主题应用有阶段：

```text
主题包校验 → 调试连接 → 注入执行 → 组件识别 → 样式生效 → 实际可用
```

前面的成功不能证明后面成功。文档里说，曾见到 `verify.log` 顶层 `pass=true`，但输入框却是 `null` 或 `0×0`。所以：

> **零匹配是未验证，不是通过。**

没找到目标，不能声称目标背景已经透明。

### 安装源、运行副本、当前页面不是一回事

本机有两份引擎 CSS：

- 安装源：`D:\Codex-Dream-Skin\CodexDreamSkin\payload\assets\dream-skin.css`
- 运行副本：`%LOCALAPPDATA%\CodexDreamSkin\engine\assets\dream-skin.css`

安装流程会把 payload 资源复制到运行目录。只改运行副本，可能被重新安装覆盖。磁盘文件改了，也不代表页面已经加载新 CSS。热加载能改当前页面，但不保存文件，页面重建后可能不保留。

排查时要分别确认：**安装源、运行副本、当前页面实际加载内容**。

### 主题开发者的职责

主题开发不只是选图片，还包括：制作和处理背景图、设计明暗配色、调整组件背景圆角阴影、配置焦点和任务背景模式、更新版本和文件校验信息、跨页面验收。

而原生容器识别失败、布局隐藏规则、组件绑定、CDP、启动和进程管理，主要属于引擎适配和运行逻辑。

### 推荐开发流程

1. 确定视觉目标。
2. 处理图片，检查人物裁切、文字区域、不同窗口比例。
3. 确定色板。
4. 配置背景行为。
5. 使用 Safe CSS 和 `data-ds-part` 接口。
6. 修改包后更新文件大小和 SHA-256。
7. 跨页面验收：首页、已有对话、输入框、菜单、弹窗、窗口缩放。
8. 记录环境和结果：已写入、已加载、已视觉确认、已交互确认。

高透明主题尤其要检查正文、代码块、次要文字、选中状态、焦点提示和弹窗可读性。

## 二、三个核心概念答疑

### DOM 是干嘛的？只有决定组件分布的作用吗？

**不是。DOM 不只是"组件分布图"，它是页面运行时的真实元素树。**

- **HTML**：设计图纸，写"应该有哪些元素、怎么嵌套"。
- **DOM**：浏览器实际建出来的"活房子"，里面有真实元素、属性、文字、层级。
- **CSS**：装修规则，决定颜色、大小、位置、透明度。
- **JavaScript**：控制行为，可以读、改、增删 DOM 元素。

DOM 的作用：

| 作用 | 说明 |
|---|---|
| 表示结构 | 页面有哪些元素，谁是谁的父节点、子节点 |
| 承载内容 | 文字、图片、按钮文字等 |
| 承载属性 | `class`、`data-*`、`id` 等 |
| 作为 CSS 目标 | CSS 选择器就是去 DOM 里找元素 |
| 作为 JS 操作对象 | 改样式、改内容、绑定事件、动态插入元素 |
| 参与布局和渲染 | 浏览器根据 DOM + CSS 计算最终画面 |

一句话：**DOM 是"页面现在实际有什么"，CSS 是"这些东西长什么样"，JS 是"这些东西怎么变"。**

### CDP 是干嘛的？只负责连接 Codex 和 Dream Skin 吗？

**不是。CDP 是 Chromium 的调试协议，连接只是第一步。**

CDP 全称是 **Chromium DevTools Protocol**，意思是 Chromium 浏览器对外暴露的一套"调试控制接口"。Dream Skin 通过它接入 Codex 的页面进程。

它不只负责连接，还能做很多事：

| 能力 | 例子 |
|---|---|
| 建立连接 | 通过 WebSocket 连到 Codex 的 renderer 页面 |
| 执行 JavaScript | `Runtime.evaluate`，在页面里跑代码 |
| 注入脚本 | `Page.addScriptToEvaluateOnNewDocument`，新页面加载时自动执行 |
| 读写 DOM | 查找元素、改元素、加标记 |
| 读写 CSS | 加样式、查计算样式 |
| 网络 / 性能 / 控制台 | 调试网络、性能、日志等 |

在 Dream Skin 里，CDP 更像一条"控制通道"：

```text
Dream Skin 启动 → 通过 CDP 找到 Codex 页面 → 执行注入脚本 → 给组件打 data-ds-part 标记 → 加载主题 CSS → 观察页面变化并补样式
```

所以：**CDP 不是单纯连接线，而是 Dream Skin 能操作 Codex 页面的底层能力。** 连接只是入口，后面执行代码、注入、查询、改样式都靠它。

### Safe CSS 的作用是什么？没有 safe.css 会影响别人使用吗？

先纠正一个关键点：**Safe CSS 不是主题包必须带的文件，它通常是引擎端的策略文件 `safe-css-policy.json`。** 你开发的主题包没有 `safe.css`，很正常。

Safe CSS 的作用：**引擎规定主题 CSS 能改哪些组件、哪些状态、哪些属性**，像"装修规定"：

- 哪些房间能装修：`root`、`sidebar`、`main`、`header`、`message`、`composer`、`dialog` 等；
- 哪些状态能写：`hover`、`focus-visible`；
- 哪些属性允许：背景、文字、边框、圆角、阴影、字体、间距、透明度、背景滤镜、部分过渡；
- 哪些属性不允许：比如 `display`、`position`、`z-index`。

**那别人用你的主题，能达到和你本地一样的效果吗？** 不一定，但"没有 safe.css"本身不是问题。关键看：

| 条件 | 影响 |
|---|---|
| Dream Skin 引擎版本是否一致 | 不同版本 Safe CSS 白名单可能不同 |
| Codex 宿主版本是否一致 | Codex 更新会改 DOM，选择器可能命中不同元素 |
| 主题包文件是否完整 | 四个文件是否齐全 |
| CSS 是否在 Safe CSS 白名单内 | 用了 `display` / `position` / `z-index` 可能别人不生效 |
| 是否使用 `data-ds-part` 接口 | 比直接追原生类名更稳 |
| manifest 校验信息是否更新 | 文件大小、SHA-256 不对可能影响加载 |

一句话总结：

> Safe CSS 在引擎端，不在主题包里。主题包没有 safe.css 是正常的。别人能否复现你的效果，取决于引擎版本、宿主版本和你的 theme.css 是否在 Safe CSS 允许范围内。

## 三、安装源和运行副本的区别

**文档里说的"安装源"和"运行副本"，指的是 Dream Skin 引擎自己的文件，不是主题包。**

```text
安装源：   D:\Codex-Dream-Skin\CodexDreamSkin\payload\assets\dream-skin.css
运行副本： %LOCALAPPDATA%\CodexDreamSkin\engine\assets\dream-skin.css
```

### 二者的区别

| 项目 | 安装源 | 运行副本 |
|---|---|---|
| 归属 | Dream Skin 安装包 / payload | Dream Skin 实际运行目录 |
| 作用 | 作为原始资源，安装或应用时被复制 | 引擎运行时读取的磁盘文件 |
| 修改后影响 | 影响以后重新安装 / 部署的结果 | 影响当前或后续运行，但可能被覆盖 |
| 风险 | 只改这里，当前页面不一定马上生效 | 只改这里，重新安装时可能被覆盖 |
| 持久性 | 更像"母本" | 更像"部署出来的副本" |

可以这样理解：**安装源 = 仓库里的原版模板，运行副本 = 已经搬到工作目录的当前版本。**

### 二者的联系

联系就是一条复制链：

```text
安装源 payload/assets/dream-skin.css
        ↓ 安装 / 应用流程复制
运行副本 %LOCALAPPDATA%\CodexDreamSkin\engine\assets\dream-skin.css
        ↓ 引擎读取并注入
当前 Codex 页面实际加载的 CSS
```

注意还有第三个东西：**当前页面已经加载的 CSS**。它不一定等于磁盘上的运行副本。

- 写入磁盘是持久化修改；
- 页面重新读取新规则，才是运行时生效；
- 热加载可以改当前页面，但如果不保存文件，页面重建后可能丢。

所以排查时要分三层看：**安装源磁盘文件、运行副本磁盘文件、当前页面实际加载的样式**，三者可能不一致。

### 对主题包开发的意义

你开发主题包时，主要改的是 `theme.css`、`theme.json`、`manifest.json`、`background.png`，而不是引擎的 `dream-skin.css`。

- 主题效果主要写在主题包的 `theme.css` 里；
- 引擎的安装源 / 运行副本，是 Dream Skin 自己的适配和基础样式；
- 别人能否复现，看引擎版本、Codex 版本、主题包完整性、CSS 是否在 Safe CSS 白名单内；
- **如果你改了引擎文件才实现效果，那别人只装你的主题包，可能达不到同样效果。**

---

## 总结

**Dream Skin 是给 Codex 做运行时换肤的引擎，Miku 是皮肤包；真正难点不在图片和颜色，而在 Codex 页面结构变化后，引擎还能不能找对组件、不误伤内容、并让样式真正生效。**

**安装源和运行副本是引擎自己的两份文件：安装源是原始母本，运行副本是实际运行用的部署副本；主题包是另一层内容。二者关系是"引擎负责加载主题"，不是同一个东西。**

## 附：专业名词小抄

| 名词 | 通俗解释 |
|---|---|
| 宿主应用 | 被换肤的软件本体，这里指 Codex 桌面端 |
| 外观引擎 | 负责接入、识别、注入、适配的中间层，这里指 Dream Skin |
| HTML / DOM / CSS / JS | 网页骨架 / 运行时元素树 / 外观 / 行为 |
| CDP | Chromium DevTools Protocol，调试协议，可连页面执行操作 |
| WebSocket | 长连接通信方式，用于建立调试连接 |
| Runtime.evaluate | CDP 命令，在页面里执行 JavaScript |
| 注入 | 运行时往页面里加代码或样式 |
| data-ds-part | Dream Skin 给主题开发者提供的组件标记接口 |
| MutationObserver | 监听 DOM 变化的工具，页面一变就重新检查 |
| Safe CSS | 主题 CSS 安全白名单，限制能改哪些组件和属性 |
| alpha / opacity | 颜色透明度 / 整个元素透明度 |
| SHA-256 | 文件指纹，校验主题包是否被改动 |
| app.asar | Electron 应用常见打包文件，本次没改它 |
| 回环地址 127.0.0.1 | 本机地址，连接的是自己电脑 |
| 零匹配 | 查询没找到目标元素 = 未验证，不是通过 |
